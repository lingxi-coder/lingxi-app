# ChatView Transcript Scroll Stability Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stop the iOS conversation transcript from going blank and from jumping to wrong positions, by removing the five structural defects in the scroll container and its data pipeline — without inverting the list.

**Architecture:** Keep the list in natural order (oldest → newest) with `.defaultScrollAnchor(.bottom)`, which on iOS 17+ already governs both the initial offset and content-size changes. Remove the redundant outer `LazyVStack` that hides the real content height from that anchor; stabilise row identity so a streaming tool group does not change its `ForEach` id mid-turn; memoise the timeline projection behind `didSet` invalidation so it is built once per mutation instead of 3–4 times per body; stop animating the follow-scroll during streaming; and replace the `onAppear`/`onDisappear` + drag-direction heuristic for "is the reader at the bottom" with a direct `onScrollGeometryChange` measurement (iOS 18).

**Tech Stack:** SwiftUI (iOS 18 deployment target), XCTest, XcodeGen (`project.yml` is the source of truth; `LingxiCode.xcodeproj` is generated).

**Spec:** This document — the analysis it argues from is recorded inline in "Background: why not inverted" below.

## Background: why not inverted

The obvious fix for a chat list is to invert it (reverse the data, flip the scroll
view and each row) so the newest row sits at content offset 0 and never needs a
position correction. That is what Stream's SwiftUI SDK, Telegram-iOS, React
Native's `FlatList inverted`, and Android's `reverseLayout` all do. It was
evaluated and **rejected for this surface**, for one reason:

Inversion trades the "loading older history shifts my view" problem for the
"content growing above my viewport shifts my view" problem. A classic chat app
wants that trade — messages arrive whole, and pagination happens constantly. This
surface is the opposite: there is **no pagination** (the whole session is loaded
at once), and the newest row **grows continuously** (streamed assistant text,
tool output, reasoning). Inverted, that growing row sits above the viewport in
content coordinates whenever the reader has scrolled up, so every token would push
what they are reading downward. In natural order the growing row is below the
viewport and cannot disturb them at all.

The React Native ecosystem carries the same conclusion as a standalone library —
`react-native-streaming-message-list` exists specifically because `FlatList
inverted` cannot handle "the last item grows over time (streaming AI responses)".

A secondary SwiftUI-specific factor: inverted, the growing row is off-screen, so
`LazyVStack` may not instantiate it and its height is estimated; the estimate is
corrected when it is finally instantiated, producing an extra jump. In natural
order an estimation error on an off-screen trailing row does not move the reader.

### Task 2: Stabilise tool-row identity across the 1→2 tool transition

`ConversationTimelineView.segments(in:)` gives a tool group one `ForEach` id when
it holds a single tool (`tool:<runID>:<traceID>`) and a *different* id once a
second tool arrives (`timeline-batch:<groupID>`). During a live turn a group grows
from one tool to two, so the id changes mid-stream and SwiftUI diffs it as
"remove one row, insert another" — tearing down and rebuilding the subtree, which
is a direct cause of the position jumps.

The fix is to give both shapes the same, group-derived id. The group id for a tool
group is `run:<runID>:tools:<firstToolID>` (`ConversationExecution.swift:99`) and
is stable as tools are appended, because it is keyed on the *first* tool.

This task deliberately does **not** change when batching kicks in. The height
change when a second tool arrives (two expanded rows collapsing into one summary
line) is existing product behaviour, not a defect; only the identity churn is.

**Files:**
- Modify: `clients/ios/Sources/Conversation/ConversationTimelineView.swift:108-117` (`flushTools`)
- Modify: `clients/ios/Sources/Conversation/ConversationTimelineView.swift:119-141` (the `for row in group.rows` loop that builds `pendingTools`)
- Test: `clients/ios/Tests/ConversationTimelineSegmentsTests.swift` (create)

**Interfaces:**
- Consumes: `ConversationTimelineGroup` (`id`, `runID`, `rows`, `status`) and
  `ConversationTimelineRow` from `ConversationExecution.swift`.
- Produces: `ConversationTimelineView.segmentIDs(in:) -> [String]`, a new
  `static` function that returns the `ForEach` ids a group projects to. It exists
  so the identity rule is testable without instantiating a SwiftUI view; the
  private `segments(in:)` is refactored to call the same id-building helper.

### Task 4: Memoise the timeline projection

`ConversationModel.visibleTimelineGroups` (`ConversationSource.swift:357`) is a
computed property that runs `ConversationRenderLayout.timelineGroups(items)` on
every access. That function walks every item and builds two collections before
emitting the groups. `ChatView` reads it at least twice per `body`
(`visibleTimelineItemCount` on line 368, then the view itself on 317 or 331), and
`body` is re-evaluated on every streamed token.

All three inputs — `items`, `selectedAgentID`, `agentTranscripts` — are `@Published`
stored properties on a class, so a `didSet` on each is a single choke point that
covers all ~25 mutation sites without touching any of them.

**Files:**
- Modify: `clients/ios/Sources/Conversation/ConversationSource.swift:314` (`items`)
- Modify: `clients/ios/Sources/Conversation/ConversationSource.swift:322` (`selectedAgentID`)
- Modify: `clients/ios/Sources/Conversation/ConversationSource.swift:325` (`agentTranscripts`)
- Modify: `clients/ios/Sources/Conversation/ConversationSource.swift:357-359` (`visibleTimelineGroups`)
- Modify: `clients/ios/Sources/Conversation/ChatView.swift:296-338` (`messageList`)
- Test: `clients/ios/Tests/ConversationTimelineCacheTests.swift` (create)

**Interfaces:**
- Consumes: `ConversationRenderLayout.timelineGroups(_:) -> [ConversationTimelineGroup]`.
- Produces: `ConversationModel.timelineGroupsRebuildCount: Int` — a
  `private(set)` counter incremented each time the projection is actually rebuilt.
  It exists so the memo is testable; it is never read by production code.

### Task 6: Measure "at the bottom" instead of inferring it

`followsLatest` is currently derived from two unreliable signals: the `onAppear`/
`onDisappear` of a 1pt `Color.clear` inside a lazy stack (which fire on cell
creation and recycling, not on visibility, and fire out of order during layout),
and the sign of a `DragGesture` translation. The whole `TranscriptScrollFollowState`
machine — the detached timestamp, the 30-second auto-resume — exists to paper over
that unreliability.

iOS 18's `onScrollGeometryChange` reports the real offset, so the question becomes
directly answerable and the machine collapses to one comparison.

This removes the 30-second auto-resume. That was a recovery hatch for
false-negative detachment; with a true measurement it is not needed, and yanking a
reader to the bottom 30 seconds after they deliberately scrolled up is worse than
leaving them alone.

```swift
enum TranscriptScrollFollowState {
    /// How far above the true bottom still counts as "at the bottom". Absorbs
    /// rounding and the one frame between a row growing and the follow scroll
    /// landing, without swallowing a real upward drag.
    static let bottomSlack: CGFloat = 24

    /// Whether the reader is parked at the newest content.
    ///
    /// Measured, not inferred. `contentOffset` may exceed the maximum while the
    /// scroll view rubber-bands, and `contentSize` may be smaller than the
    /// container when the transcript is short; both of those are "at the bottom".
    static func isAtBottom(
        contentOffset: CGFloat,
        contentSize: CGFloat,
        containerSize: CGFloat,
        bottomInset: CGFloat,
        slack: CGFloat
    ) -> Bool {
        let maximumOffset = contentSize - containerSize + bottomInset
        guard maximumOffset > 0 else { return true }
        return contentOffset >= maximumOffset - slack
    }
}
```

  the top of the viewport and let the answer grow downward, rather than pinning
  the bottom. For turns whose tool output and reasoning far exceed one viewport,
  that is a meaningfully better reading experience. It is a UX change, not a bug
  fix, and was explicitly deferred.
