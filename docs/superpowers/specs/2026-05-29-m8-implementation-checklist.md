**The proven tool-extraction recipe (per crate):** (1) `git mv` the tool files into `tools/<cat>/src/`; (2) move any cross-tool helper to `tool-api/util`; (3) write `Cargo.toml` + `lib.rs` with `register_all(reg, ctx)`; (4) repoint imports `crate::{builtin,context,progress,shared,tool_trait}::…` → `tool_api::…`; (5) in the monolith, delete the modules, `pub use tool_<cat>::{types + modules-under-old-names}`, and delegate `register_all_builtin_tools`; (6) extend `resolve_tool_src()` in the two source-scanning parity tests.

**Key coupling points discovered (must be resolved to finish P5b/P7):** all 41 tools share (1) `BuiltinToolContext` [resolved in P5a], (2) `tools/src/shared/{path_validation,output_truncation,file_kit,ansi_strip}.rs` helpers, (3) the 551-line `test_support.rs` fixture, (4) cross-tool utilities like `file_read::ulid_or_uuid`. Parity tests in `test-harness` read tool source files by path, so every file move must update those test paths. This makes P5b/P7 a genuine multi-day effort rather than a mechanical sed.

## §1 Executive Summary

M8 restructures the workspace from a `crates/`-wrapped, `lingxi-`-prefixed, tool-monolith layout into a flat, composition-root architecture where one engine assembles into separate desktop and mobile binaries. ## §3.P3 Extract tool-api crate

> Design doc reference: §9.1 row **P3**, §13 ledger entries tagged P3. Estimated **4h**. Prereq: **P2**.

#### Summary

Carve a new root-level `tool-api/` crate out of the current `tools/` monolith so engine-side consumers can depend on the abstract `Tool` trait, `ToolUseContext` (`ToolCtx`), and `ToolRegistry` surface without pulling in the 41 builtin implementations. This is a packaging move: trait semantics, error variants, and field shapes stay byte-equivalent, and the existing `tools/` crate re-exports everything from `tool_api::*` so every current `use tools::…` (post-P2 the `lingxi-` prefix is gone) keeps compiling. The §5 reshape of `ToolCtx` (full Platform handles, `ToolResult`, `ToolSchema`) is explicitly deferred to P4+.

- **P0** repo rename `lingxi-core/` → `lingxi-code/`

## §3.P4 Migrate engine deps to tool-api

> Design doc reference: §9.1 row **P4**, §13 ledger entries tagged P4. Estimated **10h**. Prereq: **P3**.

#### Summary

Phase P4 (~1d) migrates engine-side crates (`orchestrator`, `agent`, `core`, `hooks`, `coordinator`, `plugin`, `sidequery`, `skills`, `commands`) from the monolithic `tools` crate to the new `tool-api` crate created in P3, then deletes the `ToolInvoker` indirection trait (`traits/src/tool_invoker.rs`, `tools/src/tool_invoker_impl.rs`) and the orchestrator-owned `tools/src/dispatcher.rs`. #### Risks

- **Layering inversion when `SubagentInheritance.registry: Arc<tool_api::ToolRegistry>`**: P3's dep order is `tool-api → traits`, so making `traits` depend on `tool-api` creates a cycle. Mitigations, in preference order: (a) leave `tool_invoker` as a one-method shim in `traits/` for now and only delete the impl + dispatcher (split the §13 ledger's P4 row across P4 and a later cleanup phase) — but the design doc explicitly schedules deletion in P4; (b) move `ToolRegistry` itself out of `tool-api/` into a smaller `tool-registry/` crate that both `traits` and `tool-api` depend on (rejected — splinters §5 design); (c) carry the parent registry as an `Arc<dyn std::any::Any + Send + Sync>` opaque in `SubagentInheritance` and downcast inside `agent/`. Recommendation: **(c)** for P4, document it as a planned cleanup, and let P11/P12 pick up a cleaner aggregate when `Engine::builder()` lands.
- **`ToolUseContext` reshape ripple**: `turn_loop.rs` (lines 290-313) and `tools/src/builtin/agent.rs` (line 444) construct `ToolUseContext` with 11 fields including `subagent_registry`, `content_replacement_state`, `session`, `messages`, `mcp_clients`. The §5.1 `ToolCtx` is much narrower (FS / HTTP / process / sandbox / clock / permission / mcp / lsp / swarm / runtime / session_id / agent_id / cwd / model / abort). Either: (a) keep the rich `ToolUseContext` as the runtime ctx in `tool-api` (the design hints this in §13: "re-shaped; now gets full Platform handles"), or (b) ship a transitional `ToolUseContext` alongside `ToolCtx` in `tool-api`. P4 assumes P3 made this call; if not, P4 sub-blocks and we widen P3's footprint.
- **`tools::content_replacement::ContentReplacementState` is consumed by `agent/`** — a clean migration moves it into `agent/`, but the type is referenced by `tools/src/builtin/agent.rs` and `tools/src/context.rs`. Inlining into `agent/` would create an `agent → tools` edge from those builtin files; safer to **promote `ContentReplacementState` into `tool-api/src/content_replacement.rs`** (or `protocol/` if it's pure data) and re-export. Flag as a minor design decision for P4 to resolve.
- **`tools` crate tests reach into internals** (`tools::tool_invoker_impl::RegistryToolInvoker`, `tools::dispatcher::*`) — deleting the modules forces edits to `tools/src/builtin/agent.rs` tests too. They're already in scope (step 6).
- **`commands/src/builtin/{cost,compact}.rs` use `lingxi_tools::registry::ToolRegistry::new()`** inside `#[cfg(test)]` blocks — counted as source per `src/` location. Easy swap; flagged so reviewers do not miss them.
- **`sidequery::cache_safe_params::CacheSafeParams.tool_use_options: lingxi_tools::ToolUseOptions`** is a public struct field surfaced in cache keys — changing the type silently affects cache hashing. If `ToolUseOptions` survives the P3 reshape (rename only), keep the rename mechanical. If it's renamed/restructured, sidequery cache-key parity is at risk — add a parity assertion in `test-harness`.
- **Engine tests in `orchestrator/tests/` impl `Tool` against `tools::tool_trait::*`** (orchestrator_multi_turn, orchestrator_tool_error, streaming_concurrent_tools, streaming_mid_stream_tool, streaming_multi_turn, orchestrator_real_tools, registries_wiring, cost_recording, jsonl_persistence, etc.). Swapping every fixture is mechanical but high-touch; budget a second pass on test failures.
- **`AgentTool::test recursion-lock` currently relies on `Arc::downcast` via `as_any()`** on `ToolInvoker`. After step 6 the assertion compares `parent_registry` to `inherit.registry` directly — make sure the simplified test still pins the recursion-lock contract, otherwise we lose the M4-05 byte-locked guarantee silently.
- **`telemetry::tengu::orchestrator` event ids referencing tool dispatch** — `orchestrator/src/turn_loop.rs` emits orch events around tool calls; the dispatcher delete must preserve emit cadence (started / completed / failed) end-to-end.
- **Workspace fmt/clippy churn**: deleting two whole modules can trigger unused-import lints elsewhere. Plan a `cargo fmt --all && cargo clippy --workspace --fix` polish at the end.

## §3.P8 Skill split

> Design doc reference: §9.1 row **P8**, §13 ledger entries tagged P8. Estimated **8h**. Prereq: **P6**.

#### Summary

Phase P8 splits today's monolithic `crates/skills/` (Cargo name `lingxi-skills`) into two crates at the post-P1/P2 root layout: a new abstraction crate `skill-api/` (containing the `Skill` trait, `SkillRegistry`, `SkillCtx`, frontmatter loader, MCP-builder helpers, prefetch placeholder, error types) and a `skills/builtin/` plugin crate (Cargo name `skill-builtin`) that ships the in-tree built-in skill templates and exposes the `register_desktop(&mut SkillRegistry)` / `register_mobile(&mut SkillRegistry)` entry points called from `apps/engine-{desktop,mobile}/`. Today there are no compiled-in built-in skills in `crates/skills/` (skills are markdown loaded from disk), so `skill-builtin` initially holds the loader plumbing for bundled templates plus empty `register_desktop` / `register_mobile` shells that future milestones will populate; the loader / registry / frontmatter machinery moves into `skill-api`. Consumers `crates/plugin/src/manager.rs` and `crates/tools/src/builtin/skill.rs` (doc-strings + the `SkillLoader` seam) are repointed at the new crate names.

#### Prerequisites

- P0 (repo rename `lingxi-core` → `lingxi-code`)
- P1 (drop `crates/` wrapper; engine crates flat at root)
- P2 (drop `lingxi-` prefix; `lingxi-skills` → `skills` at that point, before this phase splits it)
- P3 (`tool-api/` already extracted; defines the abstraction-crate pattern this phase mirrors)
- P4 (engine deps already migrated to `tool_api`; removes the old `ToolInvoker` indirection that `crates/skills/src/skill_tool.rs` works around)
- P5 + P7 (`tools/*` per-category crates exist so `skills/builtin` does not need to depend on the old monolithic tools crate; the residual `SkillTool` model-visible tool will live in `tools/skill/` per §4.1, not in `skills/builtin/`)

Without P3 there is no `*-api/` convention to copy; without P7 the `tools/skill/` crate that owns the model-visible `Skill` tool dispatcher does not exist yet and `skills/builtin` would have to depend on the legacy monolithic `tools` crate.

## §3.P11 Mobile tool skeletons + engine-mobile composition

> Design doc reference: §9.1 row **P11**, §13 ledger entries tagged P11. Estimated **8h**. Prereq: **P10**.

#### Summary

P11 introduces the three mobile-exclusive tool crates (`tools/camera/`, `tools/voice/`, `tools/share/`) as pure-Rust skeletons that call `Arc<dyn CameraControl>` / `Arc<dyn VoiceRecorder>` / `Arc<dyn SharingService>` from `ToolCtx`, adds the matching `#[uniffi::export(callback_interface)]` traits to `traits/`, and creates the `apps/engine-mobile/` composition lib that wires the mobile tool/skill/command set (cross-OS tools + camera/voice/share + `skill-builtin::register_mobile` + `command-core` + `command-mobile`) on top of `Engine::builder()`. ## §7 Rollback Strategy

| Phase group | Rollback method |
|---|---|
| P0–P2 (rename/flatten/prefix) | Pure `git reset --hard` of the single mechanical commit. No code logic changed. |
| P3–P5 (tool-api + first tools) | Branch revert. The `tools/` re-export shim means reverting P4/P5 restores the monolith path. |
| P6–P9 (composition + remaining tools + skills + commands) | Per-phase branch revert; each is an atomic commit (P7 sub-commits revert individually). |
| P10–P11b (mobile skeletons) | Branch revert; mobile crates are leaves — reverting cannot break desktop. |
| P12 (UniFFI) | Revert Rust **and** Swift/Kotlin together in one commit — they are co-dependent via generated bindings. |
| P13–P15 (bridge/CI/cleanup) | Branch revert. P14's `deny.toml` can be disabled independently if it blocks an emergency. |
| Nuclear option | `git checkout v0.8.0` tag (M7) and cherry-pick any independent fixes forward. |
