# 开发环境与依赖身份

初始化四仓环境、增量构建，并避免在 SDK 联合开发时混用本地与固定来源的 Rust 类型。

<a id="layout"></a>

## 目录与先决条件

将 lingxi-app、harness-runtime、llm-client 和 mobile-linux-runtime 放在相邻 checkout。Rust 由 rust-toolchain.toml 固定；JavaScript 包使用 npm 与各自 package-lock.json；当前 Vite/Electron Vite 工具链要求 Node ^20.19.0 或 >=22.12.0。原生构建还需要 Gradle/NDK 或 Xcode。SDK 与产品测试仍在各自仓库运行。

### 产品初始化

```sh
cd lingxi-app
./apps/setup.sh
# Website/documentation dependencies
npm --prefix apps/web ci
```

验证方式: 需环境验证

<a id="identity"></a>

## 解析产品实际消费的 SDK

源码解析器检查锁定 Cargo metadata、规范 URL、完整 revision 与包目录归属，并拒绝重复或非预期身份。应使用解析器，不能猜测 Cargo 缓存路径。当前九成员产品 workspace 包含 apps/audio-provider；默认成员选择桌面产品包。

### 检查固定来源

```sh
cd lingxi-app
python3 scripts/lib/runtime_source.py --root
python3 scripts/lib/mobile_linux_source.py --root
cargo metadata --locked --format-version=1 --all-features
```

验证方式: 需环境验证

## 工作树 SDK 消费者

工作树示例要求本地 checkout 与显式完整依赖 overlay。仅为 Harness 设置 path 依赖不会替换它的 Git 固定 LLM 和 Mobile Linux 边。示例验证器创建隔离快照，对匹配来源 URL 设置 patch，并检查各 SDK 包路径，不改产品清单或锁文件。离线验证使用 SDK 锁文件初始化隔离消费者锁，以保留已缓存的第三方依赖版本。

- [Harness 消费者依赖配置](harness.md#installation)

<a id="incremental"></a>

## 按平台增量修改

- Electron 使用 bridge-client 的 dist 导出，因此应先构建共享包。Rust Bridge 修改需要重建二进制；仅渲染层修改可以复用。
- FFI 签名改变时，应先重新生成绑定，再编译 Kotlin 或 Swift。纯原生界面修改可复用匹配绑定。
- 翻译与语音配置的权威来源位于 resources；应运行生成与检查工具，而非直接修改生成的原生输出。

<a id="upgrade"></a>

## 依赖升级

1. 独立验证已修改 SDK 并审查公共契约。
2. SDK 拥有经审查固定 revision 后，将消费者中该仓库的依赖统一到同一规范 URL 与 revision。
3. 审查锁文件与来源解析结果，再更新受影响绑定、API 目录和手册基线。
4. 先运行定向集成检查，再进行打包或平台验收。
