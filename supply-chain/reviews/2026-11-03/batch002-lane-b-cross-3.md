## block-padding 0.3.3 and 0.4.2 — hold both unconditional proposals

IDs `registry+https://github.com/rust-lang/crates.io-index#block-padding@0.3.3`, archive `a8894febbff9f758034a5b8e12d87918f56dfc64a8e1fe757d65e29041538d93`; and `registry+https://github.com/rust-lang/crates.io-index#block-padding@0.4.2`, archive `710f1dd022ef4e93f8a438b4ba958de7f64308434fa6a87104481645cc30068b`. Read each complete `src/lib.rs` and both manifests; no build script. These implement byte and typed block padding. Both `Pkcs7`/`Iso10126` unpad through a helper that reads `block[block.len()-1]`; ANSI X9.23 does likewise. Empty raw blocks therefore panic, whereas the public trait promises an error for malformed padding without a documented empty-input panic exception. Both implementations also branch and short-circuit based on padding bytes, with no constant-time guarantee; exposing padding errors or timing before authentication can contribute to an oracle. 0.3.3 also contains `unpad_blocks` unsafe flattening, relying on the separate generic-array `ArrayLength` layout contract and a checked returned length; 0.4.2 delegates flattening to separately reviewed hybrid-array and denies crate-local unsafe.

These are independent low-level observations, not proof that this App's current typed-block consumers accept empty attacker-controlled data, that an oracle is reachable, or that a cryptographic exploit exists. A nonzero fixed block size and authenticated input before error/timing exposure can limit the risks, but a general package-wide deploy criterion needs explicit judgment about the public raw API's reasonable untrusted-input use. Hold both proposed records pending that judgment, further consumer evidence, or repair. No extra panic or timing probe was necessary to establish the source-level branches; no test or platform run was performed for these two packages.
