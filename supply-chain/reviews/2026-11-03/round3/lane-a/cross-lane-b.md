## stable_deref_trait 1.2.1 — support full safe-to-deploy

Registry archive SHA-256 `6ce2be8dc25455e1f91df71bfa12ad37d7af1092ae736f3a6cd0e37bc7810596`; 9 archive members. Mutating methods not covered by that trait contract remain the consumer's responsibility.

I checked all **23** shipped unsafe impls (`src/lib.rs:158-202`) and their feature gates: allocation-backed Box/Vec/String, std CString/OsString/PathBuf; borrowed or owned Cow; Rc and pointer-atomic Arc; Ref/RefMut and standard lock guards; shared and mutable references. Owned containers and standard guards keep their dereference target in place through moves under the trait's stated access restrictions; `Arc` is gated on pointer atomic support. Unsafe implementations by downstream types and their consumers must separately uphold the contracts. No crate-local violation was identified. The upstream source contains no executable tests; lane B supplied Rust 1.94 host reference/doc tests and cross-target compilation logs, which I inspected as supplementary evidence, not as all-platform runtime proof. ## untrusted 0.9.0 — support safe-to-run; hold safe-to-deploy

Registry archive SHA-256 `8ecb6da28b8a351d773b68d5825ac39017e680750f980f3a1a85cd8dd28a47c1`; 19 archive members. Read all `src/{lib,input,no_panic,reader}.rs`, `tests/tests.rs`, manifests, CI workflow and shipped helper scripts. No crate dependencies, build.rs, unsafe, process, network, filesystem or allocation in the runtime library. `Input` holds a slice; `Reader::read_byte` uses checked slice access, `read_bytes` checks addition and subslice bounds, and debug output omits input and cursor details. The packaged `mk/install-build-tools.sh` can install system packages / alter repositories when deliberately run, and coverage scripts have filesystem/process effects; they are CI helpers, not invoked automatically by ordinary Cargo build/test. Do not mistake permission to execute arbitrary packaged helpers for the `safe-to-run` conclusion.

There is a substantive public safe-API invariant failure. `Input::read_all` (`input.rs:64-74`) checks only the reader as it exists *after* its callback, not whether it still represents the original input. `read_all_optional` in `lib.rs:101-119` has the same structure. `Reader::read_partial` (`reader.rs:111-118`) saves an index, then assumes the callback has not replaced the reader when slicing, and unwraps that slice. Callers can replace a `&mut Reader` using entirely safe Rust; documentation does not prohibit it. Lane B's test explicitly assigns `*cursor = Reader::new(...)`, after which `read_all` can return success while the original input remains unread, and replacing a reader whose saved start is 2 with a reader at 0 makes `read_partial` panic. I independently recompiled the exact package with rustc 1.94.0 and reran those two source tests; both counterexamples reproduced (`probe/untrusted-invariant-cross.out`, panic caught by the test). The failure requires callback code to replace/reset the reader; attacker-controlled bytes alone do not do that. The test does not establish memory unsafety, a product exploit, or a vulnerability in any particular consumer.

The current lock names ring 0.17.14 and rustls-webpki 0.103.16 as consumers. In the latter, `signed_data.rs:119-125` calls `read_partial`; its direct `expect_tag_and_get_value_limited` / `read_tag_and_get_value_limited` chain in `der.rs:95-105,152-216` uses forward reads and does not replace the reader. A targeted textual search across both source trees did not identify an obvious reader replacement, but is not a complete whole-program proof of all callbacks or runtime control. Lane B's bounded reference tests support ordinary forward cursor operations, not the replaced-reader case. Since the package explicitly promises full-consumption checking and panic-free handling for untrusted parsing, and replacement is permitted by the public safe type, I cannot currently exclude a serious validation/availability consequence under reasonable callback use. Therefore **hold full safe-to-deploy** pending independent resolution of this interface risk or a corrected version, even though the current product path has not been shown exploitable. I support the narrower `safe-to-run` criterion for ordinary controlled Cargo builds/tests, recording the counterexample and the opt-in scripts; it does not meet or close the required deploy criterion.
